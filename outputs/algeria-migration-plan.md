# 阿尔及利亚项目迁移计划

## 1. 迁移目标

本次迁移目标是将阿尔及利亚项目从现有环境平滑迁移到新的高可用环境，完成数据库和 MinIO 数据迁移、应用服务高可用部署，并对当前已启用的新 DNS 入口进行核验，保留可回滚能力。

核心目标：

- 保证数据库和 MinIO 数据完整可恢复。
- 新环境具备容灾能力，避免 HA 单点故障。
- 当前 DNS 已是新 DNS，迁移期间重点核验解析和入口连通性，不再按旧环境到新环境的 DNS 切换处理。
- 迁移前可用环境在观察期内保留，必要时可快速回滚。

## 2. 时间计划

到现场后，在服务器资源、网络策略和访问权限准备完成的前提下，执行新版本 HA 迁移，预计 `1 个工作日` 完成。

计划节奏：

1. 检查服务器、网络、磁盘、DNS 和证书等基础条件。
2. 执行数据库和 MinIO 迁移前备份。
3. 部署新版本 HA 环境。
4. 还原数据库和 MinIO 数据。
5. 执行业务验证、DNS 入口核验和迁移后观察。

## 3. 服务器资源规划

以下资源为完成集群的最低要求。新 HA 部署和业务验证完成后，旧服务器资源可逐步释放，并将业务扩容到新的 HA 资源上。仲裁节点不部署在任一业务机房，其余节点平均分布在两个机房。

| 角色 | 数量 | 建议配置 | 主要用途 |
| --- | ---: | --- | --- |
| 仲裁节点 | 1 台 | 8C / 16G / 100G（60G 系统盘 + 40G 数据盘） | 第三仲裁 |
| 服务应用节点 | 2 台 | 8C / 16G / 100G（60G 系统盘 + 40G 数据盘） | 服务应用集群 |
| MySQL、MinIO、Redis | 2 台 | 8C / 16G / 460G（60G 系统盘 + 4*100G 数据盘） | MySQL/Redis 集群，MinIO 双单节点 replication |
| IM 应用节点 | 4 台 | 8C / 16G / 460G（60G 系统盘 + 4*100G 数据盘） | IM 应用集群 |
| 合计 | 9 台 | 72C / 144GB / 3060G | 约 3.06TB 磁盘 |

## 4. 数据库备份计划

步骤：

1. 执行迁移前全量备份。
2. 将备份文件复制到备份存储和新环境。
3. 在新环境执行恢复演练，确认恢复耗时和数据完整性。
4. 正式迁移前进入维护或停写窗口，执行最终备份或增量同步。
5. 数据恢复后校验核心表、关键数据量和业务连接。

## 5. MinIO 备份计划

步骤：

1. 统计 bucket 列表、对象数量、总容量、用户、策略、access key、生命周期和复制策略。
2. 对主写 MinIO 执行对象备份或 `mc mirror` 同步，并校验备节点 replication 数据是否一致。
3. 导出并记录 bucket policy、用户策略、访问权限等元数据。
4. 抽样校验对象大小、ETag/hash 和业务读取结果。
5. 记录预同步耗时、剩余增量规模和 replication lag。

## 6. 新 HA 环境部署

### 6.1 基础环境部署

1. 初始化操作系统和基础安全配置。
2. 配置主机名、内网 IP、DNS、NTP 和防火墙。
3. 挂载数据盘并设置开机自动挂载。
4. 安装 Docker 或项目所需运行时。
5. 配置系统日志、磁盘监控和基础告警。

### 6.2 数据库 HA 部署

1. 在 3 台数据库节点部署数据库服务。
2. 配置数据库 HA，MySQL InnoDB Cluster。
3. 确认主节点、从节点、复制状态和故障转移能力。
4. 创建业务所需数据库、用户和权限。
5. 恢复迁移数据并执行一致性校验。

### 6.3 MinIO 容灾部署

1. 在 2 台节点分别部署单节点 MinIO。
2. 配置独立数据盘、服务参数、控制台和内部访问地址。
3. 创建 bucket、用户、策略和访问权限。
4. 配置 bucket replication，确认主写节点到备节点的对象同步正常。
5. 恢复对象数据并执行读写、同步和故障切换校验。

### 6.4 应用 HA 部署

1. 在应用节点部署业务服务多实例。
2. 应用连接新数据库和新 MinIO。
3. 配置服务健康检查。
4. 配置负载均衡后端节点。
5. 验证应用启动、日志、接口、登录和核心业务流程。

## 7. 数据库和 MinIO 还原流程

正式还原顺序建议如下：

1. 确认新数据库 HA 集群状态正常。
2. 将最终数据库备份恢复到新数据库。
3. 校验数据库完整性和核心业务数据。
4. 确认两个单节点 MinIO 服务状态和 bucket replication 状态正常。
5. 将最终 MinIO 对象数据和元数据恢复到新 MinIO。
6. 校验对象数量、关键文件和访问权限。
7. 修改应用配置，使应用连接新数据库和新 MinIO。
8. 启动应用服务并执行完整业务验证。

## 8. DNS 核验计划

本次不进行 DNS 切换，仅核验 DNS 解析、入口连通性和回滚记录。

### 8.1 迁移前准备

1. 确认当前业务域名解析记录、TTL、证书和负载均衡入口。
2. 确认新 HA 入口公网 IP、证书和负载均衡配置。
3. 确认新环境健康检查通过。
4. 保留迁移前 DNS 解析记录截图或导出记录，用于异常时快速恢复。

### 8.2 正式核验

1. 业务进入维护或只读状态。
2. 完成数据库和 MinIO 最终同步。
3. 在新环境完成业务验证。
4. 核验业务域名仍解析到当前新 DNS 入口。
5. 进行多地区解析验证。
6. 验证访问、登录、核心 API、文件上传下载。

### 8.3 核验后观察

迁移后建议持续观察至少 24-72 小时：

- 应用错误率。
- 接口延迟。
- 数据库连接数、复制状态和慢查询。
- MinIO 节点状态、bucket replication 状态、磁盘使用率和对象读写。
- 负载均衡健康检查。
- 服务器 CPU、内存、磁盘和网络流量。

## 9. 回滚方案

如果正式迁移后出现严重问题，可执行回滚。

建议回滚触发条件：

- 数据库恢复失败或核心数据不一致。
- MinIO 对象缺失、replication 异常、权限异常或业务文件无法读取。
- 新 HA 健康检查持续失败。
- DNS 解析正常但新环境核心业务不可用。
- 错误率、延迟或资源使用超过预设阈值。

回滚步骤：

1. 停止新环境业务写入。
2. DNS 保持当前新 DNS 记录，必要时恢复迁移前入口配置。
3. 恢复迁移前可用环境的应用写入。
4. 如新环境已产生新数据，评估是否需要反向同步或人工处理。
5. 保留新环境日志、数据库状态和 MinIO 状态，用于问题分析。

注意：回滚前必须确认新环境是否已经产生业务写入，避免新旧环境数据分叉。

## 10. 验收标准

迁移完成后，建议按以下标准验收：

- 新 HA 入口访问正常。
- 应用核心业务流程验证通过。
- 数据库 HA 状态正常，数据完整。
- 两个单节点 MinIO 状态正常，bucket replication 正常，核心文件访问正常。
- 当前新 DNS 解析和入口访问验证通过。
- 旧环境进入只读或待命观察状态。
- 迁移日志、备份文件、校验记录完整留存。
- 确认业务可用并完成验收签字或邮件确认。

## 11. 配合事项

客户侧需要提前配合确认：

- 新环境服务器资源和网络策略。
- DNS 当前记录、证书和入口配置确认人。
