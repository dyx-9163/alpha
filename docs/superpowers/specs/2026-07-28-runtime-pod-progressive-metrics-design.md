# Runtime Pods 渐进加载与静默指标刷新设计

## 背景

当前进入 AIFAR Runtime 的 Pods 页时直接请求 `includePods=true&includeStats=true`。Docker 指标采集完成前，页面把整个 Pod 表格替换为“加载 Pods”空白状态，导致名称、服务、状态、Revision 和镜像等基础信息也无法及时展示。

## 目标

- Pods 页先加载并显示基础 Pod 状态，不等待 CPU/内存指标。
- 基础状态完成后静默补齐 CPU/内存，并在页面可见期间每 10 秒更新。
- 指标刷新不触发页面级 loading，不清空基础状态或已有指标。
- 离开 Pods 页、切换服务器或实例、组件卸载后停止当前轮询；同一时刻最多一个指标请求。

## 方案

### 两阶段加载

进入 Pods 页或切换 Runtime 实例时：

1. 发起基础请求：`includePods=true&includeStats=false`。
2. 基础请求完成后立即渲染 Pod 表格。
3. 随后发起后台指标请求：`includePods=true&includeStats=true`，但不进入全局 loading。
4. 指标返回后按现有 Pod 标识合并并重新渲染 CPU/内存。

表格始终存在。基础请求进行中只在表格内部展示加载态，不再显示占满内容区的“加载 Pods”按钮。指标尚未返回时 CPU/内存显示 `-`。

### 周期刷新

- 轮询周期固定为 10 秒。
- 仅当顶层页签为 AIFAR Runtime、资源页签为 Pods、服务器与实例有效时运行。
- 进入有效作用域后，在基础请求完成时立即静默刷新一次指标，再启动周期。
- 使用单飞保护：上一轮指标请求未完成时跳过本轮，不并发堆积。
- 离开 Pods 页、切换服务器/实例或组件卸载时清除定时器；异步响应仍需校验请求作用域，旧作用域响应不得覆盖新页面。

### 手动操作

- “刷新”强制刷新基础 Pod 状态，完成后静默刷新指标。
- “刷新指标”立即触发一次静默指标请求。
- 指标按钮不使用页面级 loading；基础刷新可使用现有 loading 状态。

## 缓存与错误处理

- 基础请求成功后设置当前作用域的 Pods loaded 标记。
- 无指标的基础响应不得把已有同一 Pod CPU/内存覆盖为 `undefined`。
- 指标成功后更新 stats loaded 标记及 Pod 缓存。
- 指标失败仅记录现有错误通道并保留基础状态和最后一次成功指标；不切换为 degraded 空列表。
- 基础请求失败沿用现有页面错误提示，但表格结构保持可见，方便用户手动刷新。

## 测试

- 策略测试：进入/切换作用域先请求基础状态，指标请求为后台刷新。
- 调度测试：立即执行、10 秒周期、单飞、停止后不再执行。
- 合并测试：基础响应保留已有指标；指标失败不清空 Pod 列表。
- 组件渲染测试：未完成基础加载时仍渲染表头，不出现“加载 Pods”大空白状态。
- 完整前端测试和生产构建。

## 非目标

- 不修改后端指标 API 或改为 SSE 推送。
- 不修改坏更新包、健康检查或回滚逻辑。
- 不改变 Services 页指标展示规则。
