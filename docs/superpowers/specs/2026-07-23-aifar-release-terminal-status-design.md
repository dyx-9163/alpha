# AIFAR 发布终态修复设计

## 问题

AIFAR 单服务升级、批量升级和回滚在开始时写入 `pending` 发布记录，但远程执行失败时只会把任务标记为失败，没有同步更新发布记录。因此发布历史长期显示“等待中”。失败记录的 `activatedAt` 还是 Go 零值，前端会显示为公元 1 年。

## 目标

- 新发生的升级或回滚失败立即写入 `failed` 发布终态。
- 服务启动时把历史上仍为 `pending`、但关联任务已失败或取消的发布记录对账为 `failed`。
- 失败和等待中的发布记录不展示激活时间。
- 保留原始业务错误；发布状态补写失败只能作为附加日志，不能覆盖原错误。

## 方案

在 AIFAR 服务层增加统一的失败发布写入逻辑。三条发布链路保存 `pending` 后注册失败收口：函数返回错误时，用同一个 release ID 覆盖写入 `failed`，并在 manifest 中记录 `status`、`phase`、`error` 与 `failedAt`。

Store 增加启动对账：扫描 `pending` 发布，读取 manifest 中的 `taskId`，当任务已是 `failed`、`cancelled` 或 `timeout` 时，将发布状态统一修正为 `failed`。没有 taskId、任务不存在或任务仍在执行的记录保持不变。

API 对零值 `activatedAt` 不再输出有效时间；前端只有 `success` 发布显示激活时间，其他状态显示 `-`。

## 验证

- 覆盖单服务、批量、回滚失败终态的 Go 测试。
- 覆盖历史 pending 对账的 Store 测试。
- 覆盖失败记录 API 时间字段和前端时间显示的测试。
- 运行后端测试、前端测试和前端构建。
