# AIFAR Runtime 停机式全部重启设计

## 1. 背景与目标

当前“全部重启（读取新配置）”由 `aifar-agent restart-runtime` 对已启用服务逐副本滚动替换：新容器健康后再替换旧容器。该行为与运维人员对“全部重启”的预期不一致，也会让确认弹窗和任务步骤把该动作描述为滚动更新。

本次将“全部重启”改为明确的停机式全量重启：先下线当前实例的全部 AIFAR 业务 Pod，再根据持久化 RuntimeSpec 和当前 env 文件启动全部期望 Pod，最后统一执行健康与副本校验。该操作允许计划内业务中断，不提供滚动可用性保证。

## 2. 范围

### 2.1 包含

- 修改 `aifar-agent restart-runtime` 的执行语义。
- 调整后端任务步骤、日志和中英文文案。
- 调整前端确认弹窗中英文文案。
- 增加 Agent、应用服务和 HTTP 任务计划的自动化测试。
- 保持现有 HTTP API、Agent CLI 命令和按钮名称兼容。

### 2.2 不包含

- 不修改单服务制品发布的滚动更新能力。
- 不停止 `aifar-agent`、宿主机代理监听器或 Docker 服务。
- 不修改 RuntimeSpec 的副本数、镜像、环境变量或挂载定义。
- 不实现失败后的自动回滚，也不恢复已删除的旧容器。
- 不改变“同步运行时”和“启动/恢复 Pods”的既有语义。

## 3. 执行模型

`Manager.RestartAll` 继续持有实例 Runtime 调和互斥锁，避免周期调和、手动调和和全部重启并发修改同一实例。执行分为五个阶段。

### 3.1 读取与全量预检

Agent 规范化并校验 RuntimeSpec，然后在任何删除操作前完成以下检查：

- RuntimeSpec 的实例、网络、服务、端口和 Deployment 定义合法。
- 每个期望副本大于 0 的 Deployment 镜像可用。
- env 文件和宿主机挂载源存在且类型符合要求。
- Docker 网络存在。
- 容器启动参数能够由当前 RuntimeSpec 完整生成。

预检不再要求每个期望副本当前都存在；缺失副本应由本次全量重启恢复。任一预检失败时立即返回，现有 Pod 保持不变。

### 3.2 全部下线

预检成功后，Agent 列出并删除当前实例下带有 AIFAR Runtime 标签的全部业务 Pod，包括：

- 当前期望副本；
- 旧 revision 容器；
- 临时 replacement/backup 容器；
- 漂移或超出期望数的残留容器。

期望副本为 0 的服务不会在启动阶段恢复。每个删除失败都记录为阶段错误；Agent仍继续尝试删除其余 Pod。若下线阶段结束后仍存在无法删除的 Runtime Pod，则不进入启动阶段，避免新旧容器混合运行，并返回包含容器名称的汇总错误。

删除完成后刷新该实例 Endpoint 缓存。停机窗口内代理没有可用 Endpoint，对业务请求返回无可用后端；Agent 和代理监听器本身保持运行。

### 3.3 全部启动

Agent 按 RuntimeSpec 的 Deployment 顺序和副本序号创建全部期望 Pod，但创建成功后不等待该 Pod 健康才处理下一个 Pod。每个 Pod 的启动结果独立记录：

- 单个 Pod 创建或启动失败时，记录服务、副本和 Docker 错误；
- 继续尝试启动其余所有服务和副本；
- 期望副本为 0 的服务保持下线；
- 不创建滚动更新使用的 `next` 或 `old` 临时容器。

所有创建命令尝试完成后才进入统一校验阶段。

### 3.4 统一健康校验

Agent 在各 Deployment 的 `progressDeadlineSeconds` 约束内统一轮询已创建 Pod，直到全部期望副本 healthy 或相应截止时间到达。校验至少比较：

- desired replicas；
- current replicas；
- ready/healthy replicas；
- revision 与 spec hash 是否匹配当前 RuntimeSpec。

校验过程中刷新 DeploymentStatus 和 Endpoint 缓存。成功条件是每个已启用 Deployment 的 current、ready、updated、available 均等于 desired，且零副本 Deployment 没有运行 Pod。

### 3.5 结果汇总

全部服务满足期望时命令成功。存在启动错误、健康超时或最终副本不一致时，命令失败并汇总所有服务/副本错误；已经成功启动且健康的 Pod 保持运行，不自动回滚。

## 4. 取消语义

- 全量预检完成前取消：立即退出，不修改现有 Pod。
- 已开始下线后取消：停止后续未执行的删除或创建操作；已经删除和已经启动的 Pod不回滚。
- 统一健康校验期间取消：停止等待，保留当前容器状态并刷新可获得的最终状态。
- 任务标记为 `cancelled`，日志明确提示运行时可能处于部分恢复状态，需要重新执行“全部重启”或使用“启动/恢复 Pods”。

取消检查发生在每个外部 Docker 操作之间；已经提交给 Docker 的单个操作采用其实际完成结果，不宣称跨容器原子取消。

## 5. 控制面与用户界面

现有 HTTP 路径、请求体、权限、审计动作、按钮名称和 Agent CLI 命令保持不变。

任务步骤调整为：

1. `load-instance`：读取 AIFAR Runtime 实例；
2. `preflight-runtime`：检查 RuntimeSpec、镜像和启动条件；
3. `stop-all-pods`：下线全部 Runtime Pods；
4. `start-all-pods`：启动全部期望 Runtime Pods；
5. `verify-runtime`：统一校验服务健康和副本状态。

前端确认弹窗明确展示：

- 将先停止该实例全部业务 Pod；
- 停机窗口内全部业务不可用；
- 随后按当前 Runtime 配置和 env 文件启动全部期望副本；
- 单个启动失败不会阻止其他服务启动；
- 失败或取消不会自动恢复已删除的旧容器。

后端和前端不再使用“滚动重建”“逐个替换”“新容器健康后替换旧容器”等描述本操作。

## 6. 错误处理与可观测性

- 预检错误包含服务、镜像、文件、挂载或网络的具体对象。
- 下线错误包含无法删除或仍然残留的容器名称。
- 启动错误包含服务名、副本号、目标容器名和 Docker 返回错误。
- 健康错误包含 desired/current/ready/updated/available 数值及最后一次容器健康状态。
- Agent 在每个阶段更新 DeploymentStatus；下线和启动阶段使用现有稳定状态码 `pending`，最终使用 `ready`、`offline`、`degraded` 或 `failed`。
- 后端 worker 保留 target、step 和普通任务日志，并在任务失败时写既有失败审计结果。

## 7. 测试策略

### 7.1 Agent 单元测试

- 证明所有旧 Pod 的删除发生在任一新 Pod 启动之前。
- 证明缺失现有副本不会导致预检失败，重启会恢复它。
- 证明零副本 Deployment 保持下线。
- 证明单个 Pod 启动失败后仍尝试启动后续所有 Pod。
- 证明下线残留会阻止启动，避免新旧混跑。
- 证明启动阶段不生成 `next`、`old` 或 rename 滚动替换操作。
- 证明最终副本或健康不一致导致失败并包含全部错误。
- 证明各阶段取消遵循本设计的非回滚语义。

### 7.2 应用服务与 HTTP 测试

- 任务计划使用新的五个步骤及稳定机器码。
- 远端脚本仍调用兼容命令 `aifar-agent restart-runtime --spec`。
- 远端失败、取消和锁释放行为保持正确。
- apps.manage 权限和审计约束不变。

### 7.3 前端测试

- 确认弹窗准确传入服务数和副本数。
- 中英文文案明确停机影响、失败继续和不自动回滚。

### 7.4 验证命令

- 运行受影响的 Go 包测试。
- 运行 `pnpm test`。
- 运行 `pnpm test:web`。
- 运行 `pnpm web:build`。

不在本改动中连接真实服务器执行破坏性验收；真实环境验收需另行确认维护窗口，并验证全部旧 Pod 先消失、全部期望 Pod 随后恢复以及最终副本状态一致。

## 8. 验收标准

- 操作开始后不存在旧 Pod 与新 Pod 重叠运行的滚动阶段。
- 在第一条新 Pod 启动命令执行前，实例全部旧 Runtime Pod 已删除并复查为空。
- 某个新 Pod 启动失败不阻止其余 Pod 的启动尝试。
- 任务只有在所有期望 Pod healthy 且最终副本一致时成功。
- 页面、任务步骤和日志不再把“全部重启”描述为滚动更新。
- 单服务制品发布仍保持原有滚动更新行为。
