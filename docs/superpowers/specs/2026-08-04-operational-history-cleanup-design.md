# AIFAR 运行历史手动清理设计

## 1. 背景

控制面 SQLite 会持续写入状态历史和告警事件。当前“执行保留清理”只处理过期审计日志和已结束任务，不处理 `status_snapshot_history` 与 `alert_events`。当客户长时间运行后，这两张历史表可能显著增大数据库。

本版本新增独立的“清理运行历史”入口。该入口只由 `aifar-server` 实现，不修改、不升级也不重启 `aifar-agent`。

## 2. 目标

- 管理员可以从“面板设置 → 数据维护”手动发起运行历史清理。
- 清理不影响当前状态、当前告警、任务、审计、应用实例、发布记录、备份记录和业务配置。
- 面对超大积压时仍使用短事务渐进处理，不执行一次性大删除。
- 清理任务可取消；失败或中断后可以安全重跑。
- 清理动作具有权限校验、任务步骤、操作日志和审计记录。
- 明确区分“SQLite 内部空间可复用”和“数据库文件物理缩小”。

## 3. 非目标

- 本版本不增加自动定时清理。
- 本版本不改变采集周期。
- 本版本不提供任意表选择、任意 SQL 或“清空全部数据库”能力。
- 本版本不自动执行 `VACUUM`、`VACUUM INTO` 或数据库文件替换。
- 本版本不承诺在线操作后 `aifar.db` 文件立即变小。
- 本版本不处理客户目标服务器上的日志或诊断归档。

## 4. 清理范围

### 4.1 删除的数据

| 表 | 删除条件 | 默认保留 |
| --- | --- | --- |
| `status_snapshot_history` | `created_at` 早于本次任务固定截止时间 | 最近 7 天 |
| `alert_events` | `event = 'updated'` 且 `created_at` 早于本次任务固定截止时间 | 最近 7 天 |

截止时间在任务开始时计算并固定，任务运行期间新产生的数据不进入本次清理范围。

### 4.2 明确保留的数据

- `status_snapshots`：当前资源状态。
- `alerts`：当前告警及已恢复告警主体。
- `alert_events` 中的 `created`、`acknowledged`、`muted`、`unmuted`、`resolved` 等生命周期事件。
- `collector_runs`：采集器当前运行摘要。
- `tasks`、`task_logs`、`task_targets`、`task_steps`。
- `audit_logs`。
- 应用实例、发布、备份、凭据、设置和其他控制面数据。

删除历史记录不会改变当前监测结果或告警判断，但会减少可追溯的旧状态明细和旧告警更新明细。确认弹窗必须明确披露这一点。

## 5. 页面设计

在现有“创建数据库备份”和“执行保留清理”旁新增普通按钮：

> 清理运行历史

不修改现有“执行保留清理”的含义和行为，避免把审计/任务保留与运行历史清理混为一体。

点击后显示确认弹窗，内容包括：

- 将删除 7 天前的状态历史。
- 将删除 7 天前的告警 `updated` 更新事件。
- 当前状态、当前告警和告警生命周期事件不会删除。
- 操作以后台任务渐进执行，可在任务中心查看和取消。
- 在线删除只释放 SQLite 内部可复用空间，不保证数据库文件立即缩小。
- 建议先使用现有“创建数据库备份”完成备份。

弹窗只有“取消”和“确认清理”。本版本不提供自定义表、SQL、清空全部或自动压缩选项。

按钮仅对具有设置管理权限的用户启用。请求提交成功后提示“运行历史清理任务已创建”，并交由现有任务中心跟踪。

所有新增按钮、弹窗、错误提示、任务步骤和任务日志必须同时提供中文与英文文案，并继续使用现有前后端 i18n 机制。

## 6. 后端接口与任务

新增接口：

```text
POST /api/v2/maintenance/operational-history/cleanup
```

接口不接收表名、SQL 或自由截止时间。本版本使用后端固定的 7 天保留规则，避免前端绕过安全边界。

接口错误继续使用 `{ code, message, details }`，不得把原始 SQL、数据库路径或其他敏感信息返回前端。

接口执行以下动作：

1. 校验设置管理权限。
2. 检查是否已有运行中的同类清理任务；存在时返回冲突，不重复启动。
3. 创建任务 `maintenance.operational-history.cleanup`。
4. 保存任务目标和步骤。
5. 由 worker 异步执行。
6. 写入审计记录，包含发起人、任务 ID、截止时间、删除数量和最终状态。

任务步骤：

1. `preflight`：固定截止时间，检查数据库可用性和同类任务互斥。
2. `cleanup-status-history`：渐进删除过期状态历史。
3. `cleanup-alert-updates`：渐进删除过期告警 `updated` 事件。
4. `summarize`：记录删除数量、耗时、取消或失败原因。

## 7. 超大数据安全策略

### 7.1 禁止大事务

当前 Store 只使用一个 SQLite 连接。任何长事务都会让其他数据库操作排队。因此每个删除批次必须是独立短事务，禁止先收集全部 ID 再一次提交。

初始批次为 100 行，允许根据上一批耗时逐步调整，但上限为 500 行：

- 单批耗时低且数据库响应正常时，可以逐步增加。
- 单批明显变慢时，立即降低批次。
- 单批超过超时、数据库返回错误或任务被取消时，停止本次任务。

每批提交后主动让出执行时间。清理数据库占用时间目标不超过总运行时间的约 10%，避免持续抢占唯一连接。

### 7.2 查询方式

- 使用主键 `id` 的顺序游标查询和删除。
- 禁止 `OFFSET` 分页。
- 禁止为了展示进度执行全表 `COUNT(*)`。
- 禁止在服务启动迁移中为超大历史表同步创建大型全局索引。
- 每批已提交的删除结果就是安全检查点；任务失败、取消或服务重启后，重新点击按钮会从剩余最早记录继续，不回滚已提交批次。

任务中心只按时间间隔输出汇总进度，不为每个批次写日志，避免清理任务反向制造大量 `task_logs`。

### 7.3 异常处理

- 清理错误只使当前任务失败，不影响 `aifar-server` 启动和健康状态。
- 已提交批次不回滚；重新执行必须幂等。
- 同一时间只允许一个运行历史清理任务。
- 管理员取消任务后，在当前短事务完成时响应取消。
- 磁盘空间不足、数据库完整性错误或无法维持短事务时，任务停止并提示人工维护。

该机制允许 TB 级积压以低速方式逐步止血，但完成时间可能很长，不承诺在在线窗口内快速清空全部历史。

## 8. 物理空间回收边界

批量删除只会将 SQLite 页面加入空闲页列表，后续写入可以复用这些页面；`aifar.db` 文件通常不会立即缩小。

如果客户必须把大量空间归还给操作系统，应执行独立维护流程：

1. 将一致性备份保存到另一块磁盘并完成完整性验证。
2. 停止 `aifar-server`。
3. 在空间充足的另一块磁盘执行数据库重建或受控压缩。
4. 验证新数据库完整性和必需表。
5. 原子替换数据库文件。
6. 启动服务并验收。
7. 验收成功后再归档或删除旧数据库。

在线按钮不得自动进入该流程。

## 9. Store 与维护服务边界

Store 新增面向固定语义的批量方法，不接受表名：

- 删除一批指定截止时间以前的状态历史。
- 删除一批指定截止时间以前且事件类型为 `updated` 的告警事件。

批量方法返回本批删除数量和下一游标信息。维护 Service 负责循环、批次调节、让步、取消和统计；HTTP handler 只负责权限、任务、审计和响应，不直接执行 SQL。

## 10. 验证要求

### Store 测试

- 仅删除超过截止时间的 `status_snapshot_history`。
- 仅删除超过截止时间且类型为 `updated` 的 `alert_events`。
- 保留当前状态、当前告警和全部生命周期事件。
- 每批不超过设置上限。
- 重复执行不会误删保留范围数据。
- 中断后重跑可以继续处理剩余数据。

### Maintenance 测试

- 批次会让出执行时间并响应取消。
- 同类任务互斥。
- 单批失败后停止，已提交批次保持有效。
- 汇总数量和状态准确。

### API 测试

- 无权限用户被拒绝。
- 成功请求返回任务 ID。
- 任务计划、步骤和审计记录完整。
- 并发重复请求返回冲突。

### 前端测试

- 按钮只对有权限用户启用。
- 确认弹窗准确展示删除范围和不缩小文件提示。
- 取消确认不会发起请求。
- 成功提交后显示任务已创建。

### 回归验证

- 后端执行 `go test ./...` 或 `pnpm test`。
- 前端执行 `pnpm test:web` 和 `pnpm web:build`。
- 使用大批量测试数据验证清理期间登录、状态读取、任务列表和告警列表仍能正常响应。

## 11. 验收标准

- 页面出现独立“清理运行历史”按钮，现有保留清理按钮行为不变。
- 运行历史清理只删除约定的两类历史记录。
- 当前状态、当前告警、生命周期告警事件及其他业务数据保持不变。
- 大量记录按短事务处理，可取消、可安全重跑，不产生逐批任务日志。
- 清理失败不导致 `aifar-server` 退出。
- 页面和任务日志明确说明数据库文件不会因在线清理立即缩小。
- `aifar-agent` 无任何改动。
