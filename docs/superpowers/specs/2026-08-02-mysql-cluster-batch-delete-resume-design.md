# MySQL 三节点集群批量删除可恢复设计

## 背景

当前 `apps.delete.batch` 逐条调用应用模块的 `Delete`。MySQL 模块在每次删除前都会重新要求权威集群恰好包含三个成员。第一个成员删除成功后，本地成员数变为两个，第二个成员因此被 `MYSQL_MAINTENANCE_STATE_INVALID` 拦截，造成远端和本地记录只完成一部分。

当前现场已处于该中间状态：三个 MySQL Router 与 `.137` MySQL 已由审计任务成功删除，`.134`、`.133` MySQL 仍待删除；`.132` 是独立单机实例，必须保留。

## 目标

- 在任何远端变更前，对本批次选中的 MySQL 实例只做一次完整安全预检并冻结范围。
- 同一批次后续节点不因前一个节点已删除而重新要求三成员完整性。
- 已部分删除的集群允许选择全部剩余成员后继续清理。
- 任一剩余成员存在维护标记、恢复协调标记、归属漂移或漏选时继续拒绝删除。
- 最后一个成员删除后，自动清除已经没有成员的 `app_clusters` 记录。
- 保持 SSH 密码确认、任务步骤、目标日志、操作锁和审计链路；不提供自由 shell 或直接 SQL 删除入口。

## 方案

### 批次级预检

在应用注册协议中增加可选的批量删除预检能力。HTTP 层完成实例、服务器、密码和完整选择校验后，按应用调用预检。MySQL 预检读取最新持久化状态并验证：

1. 所选实例仍属于请求中的服务器、拓扑和集群。
2. standalone 继续使用现有维护/协调保护。
3. InnoDB Cluster 的集群记录有效，所有当前权威成员都有对应 MySQL 实例，且同一 `clusterId` 的当前实例没有游离成员。
4. 本批次选中了该集群所有仍存在的成员。
5. 所有剩余成员的 `mysqlMaintenance` 和 reconciliation 标记均不存在且可解析。
6. 完整三成员集群和成员数已经减少的中间状态都可进入删除，但中间状态只能整体删除全部剩余成员。

预检成功后，HTTP 层把仅存在于内部 Go 请求对象的批次范围附加到每个删除请求。该字段不从 JSON 解码，客户端不能自行声明已预检。

### 执行期复核

MySQL `Delete` 收到有效批次范围时，不再重复三成员拓扑校验；它仍会重新读取当前实例，核对实例身份，并确认当前成员没有新出现的维护或协调标记。没有批次范围的单实例删除继续使用原有严格校验。

### 空集群清理

`DeleteAppInstance` 在同一个 SQLite 事务中先记录实例所属的 cluster ID，删除成员和实例相关数据，然后只删除成员数已经为零的 `app_clusters`。仍有成员的集群记录不受影响，独立 `.132` 实例没有成员关系，也不会被触碰。

## 错误与安全边界

- 批次漏选任一当前成员：返回集群整体删除要求，不创建远端删除任务。
- 维护标记存在或损坏：返回维护相关稳定错误码。
- reconciliation 标记存在或损坏：返回协调恢复要求。
- 集群、成员、实例所有权不一致：失败关闭，不执行远端卸载。
- 远端某节点卸载失败：任务失败并保留尚未删除的本地记录；再次选择全部剩余成员可续删。
- 所有实际删除仍要求每台目标服务器已保存的 SSH 密码在面板中逐台确认。

## 验收

1. 三成员正常集群批量删除时，预检只发生一次，三个删除均可执行。
2. 仅剩两个权威成员且全部被选择、无安全标记时，批量删除可成功续跑。
3. 仅选择两个剩余成员中的一个时拒绝创建任务。
4. 任一剩余成员带维护或 reconciliation 标记时拒绝执行。
5. 删除倒数第二个成员后集群记录保留；删除最后一个成员后空集群记录删除。
6. `.132` standalone 记录和服务器不发生变化。
