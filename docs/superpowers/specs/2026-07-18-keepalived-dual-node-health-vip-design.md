# Keepalived 双节点健康检查与 VIP 漂移设计

## 目标

在 `192.168.74.132` 和 `192.168.74.133` 上部署 Keepalived 2.4.2，通过各节点本机的聚合健康接口控制 VIP `192.168.74.130/24`：两端健康时由 132 持有，132 失败时漂移到 133，132 恢复后自动切回。

## 节点与选主

| 节点 | 健康接口 | VRRP 优先级 | 默认角色 |
|---|---|---:|---|
| 132 | `http://192.168.74.132:38000/health/aggregate` | 150 | 首选 MASTER |
| 133 | `http://192.168.74.133:38000/health/aggregate` | 100 | BACKUP |

两节点都以 `state BACKUP` 启动，由优先级选出 MASTER。保持 Keepalived 默认抢占行为，不设置 `nopreempt`，因此 132 恢复健康后会凭更高优先级重新获得 VIP。

## VRRP 通信

- 使用 unicast VRRP，132 的 peer 为 133，133 的 peer 为 132。
- 两端使用相同的 `virtual_router_id 130`、VIP、检查脚本名称和检测参数。
- 两端的 `unicast_src_ip`、peer 地址和 priority 不同。
- 实施前分别探测实际承载网卡；若 133 不是 `ens160`，使用 133 的真实网卡名，不强行套用 132 的接口名。

## 健康判定

每台 Keepalived 只检查本机对应地址，不检查对端。检查同时满足以下条件才返回成功：

1. `curl` 在 2 秒内完成，HTTP 状态为 2xx。
2. 响应 JSON 包含布尔字段 `"up": true`。

检查脚本由 root 所有，其他用户不可写；Keepalived 启用 script security。检查周期为 2 秒，连续失败 3 次判定不健康，连续成功 2 次判定恢复。`vrrp_script` 不设置非零 weight，失败节点直接进入 FAULT 并释放 VIP。

## 状态行为

| 132 | 133 | VIP 结果 |
|---|---|---|
| 健康 | 健康 | 132 持有 |
| 不健康 | 健康 | 133 持有 |
| 健康 | 不健康 | 132 持有 |
| 不健康 | 不健康 | 无节点持有 |

预期业务失败检测约为 6 秒，加上 VRRP 状态转换通常在约 6～10 秒内完成漂移；132 恢复需要连续 2 次成功，之后由默认抢占机制切回。

## 实施与回滚

1. 只读检查两节点系统、网卡、健康接口、VIP 冲突、Keepalived 安装和 systemd 状态。
2. 若 133 未安装 Keepalived，则使用已验证的源码安装脚本安装到 `/aifar/apps/keepalived`，但暂不启动。
3. 在两节点创建相同逻辑、不同本机 URL 的健康脚本及对应 unicast 配置。
4. 两端配置均通过 `keepalived -t` 后，先启动 133，再重载或重启 132，避免配置切换期间无人候选。
5. 验证两端进程、VRRP 日志、唯一 VIP 所有者和从当前 Windows 主机到 VIP 的连通性。
6. 受控停止 132 的健康服务不在本次授权范围内；功能测试使用临时替换 132 检查脚本结果或停止 132 Keepalived，验证漂移后立即恢复，再验证自动切回。
7. 任一节点配置或启动失败时恢复该节点原配置和原服务状态；若双节点一致性未建立，保留 132 当前单节点配置与 VIP，133 保持 inactive。

## 验收标准

- 两节点 Keepalived 配置语法均通过，服务均 enabled/active。
- 两端健康时 VIP 只出现在 132。
- 模拟 132 Keepalived 不可用后，VIP 只出现在 133，且当前 Windows 主机仍能访问 VIP。
- 恢复 132 后，VIP 自动且唯一地回到 132。
- 两节点近期日志没有配置错误、脚本安全错误或双 MASTER 持续状态。

## 前置条件

- 需要 133 的可用 root SSH 凭据；不得把密码写入仓库、日志或设计文档。
- 133 的健康接口当前从 Windows 主机访问超时，实施前必须从 133 本机验证；如果本机也失败，133 保持 FAULT，不能作为可接管节点。
